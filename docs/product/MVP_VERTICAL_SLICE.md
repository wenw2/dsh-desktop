# MVP Vertical Slice：可验证的本地 Agent 任务闭环

## 文档状态

本文件是施工与验收要求，不是功能已实现或验收已通过的声明。范围限于 macOS Apple Silicon 上的 Discuss / Work；复用当前 DeepSeek Harness Runtime，不新增 Agent Loop、权限系统或凭证系统。

本次审计只完成未修改基线检查与有限 GUI 冒烟：`npm ci` 成功并应用 19 个现有补丁；`npm test` 为 668 通过、1 失败；`npm run typecheck`、`npm run build` 成功。GUI 验证了主界面、Sidebar 添加 Workspace 入口、原生目录选择器及取消、Settings / Models 入口。没有配置凭证、创建 Workspace / Session、发出 LLM 请求或执行 Agent 工具。因此，下面完整闭环尚未实测通过。精确命令、失败原因和运行证据以 [BASELINE_AUDIT.md](BASELINE_AUDIT.md) 为准。

关联文档：[产品定义](PRODUCT_BRIEF.md)、[架构边界](ARCHITECTURE_BOUNDARIES.md)、[UI 所有权与扩展点](UI_SURFACE_MAP.md)。

## 完整闭环

打开 App → 添加 Workspace → 新建 Task → Agent 读取项目 → 显示 Plan → 执行文件或命令操作 → 请求必要批准 → 显示 Changed Files / Diff → 用户接受或回滚 → Session 可以恢复。

这里的顺序描述用户经历，不意味着先执行副作用再询问许可：第 6 步发起的 Tool Action 若需要批准，必须在真正派发前进入第 7 步。

## 不可混淆的验收语义

### 1. Discuss 必须有经过验证的只读约束

目标是 Discuss 允许项目理解、问题澄清与方案审核，但不能修改项目文件、执行有变更副作用的命令，或把讨论自动转为工作执行。

上游 plan mode 不能独自满足这个目标。它通过指令引导 Agent，所有工具仍然可用；`/plan` 和 Plan review 不是安全沙箱。上游依据：[`dsh-plan-mode/README.md`](../../node_modules/@deepseek-ai/dsh-plan-mode/README.md) 的 Summary、When to choose it、Known Limitations；[`PlanProjection`](../../node_modules/@deepseek-ai/dsh-plan-mode/lib/types/types.d.ts) 只有 `active` / `pending` 状态。

施工必须先验证现有 Harness 权限与沙箱配置能否提供所需约束，不得为此复制或改写安全系统。如果现有配置不能满足，记录为阻塞，另行决策；不能仅用 prompt、模式标签、隐藏按钮或一次模型配合的演示，宣称只读保证成立。

至少需要负面测试：在 Discuss 状态要求修改专用 fixture 文件、执行有副作用命令，验证操作被既有机制阻止，且目标状态未改变。切换到 Work 必须是明确用户决定，UI 不得把尚未持久化的 `pending` 当作生效。

### 2. Plan 批准与 Tool Action 批准是两个决定

- Plan 批准：接受当前版本的工作方向与范围。
- Tool Action 批准：在现有权限策略要求时，授权具体工具、目标、命令与作用范围。

批准 Plan 不得被解释为绕过后续权限提示。Keep planning、关闭审核、取消和过期批准都不能被当作同意执行。

### 3. Changed Files / Diff 不是变更归属或回滚能力

模型声称改过某个文件，不等于磁盘确实变化；Git diff 显示变化，不等于变化全部属于当前 Task；文件可比较，不等于存在安全可用的恢复前态。

“接受”定义为保留当前工作区修改并确认已审阅，不隐含 commit、push 或创建 Pull Request。“回滚”必须有可验证的任务前态、精确目标、变更归属和冲突处理；不能用清空工作区、重置整个仓库或覆盖用户并发修改代替。

当前未确认存在可直接复用的 Git Change Set / Accept / Rollback API。这是能力缺口，不是把本步骤从 MVP 删除的理由。自动回滚的最终支持范围仍待决，不能把后文的简单测试样本当作已批准的产品范围缩减。

### 4. Session 恢复不保证外部副作用 exactly-once

上游 checkpoint 记录调用意图和已持久化结果；进程可能在外部动作完成、结果落盘之前退出。此时不能知道动作是否完成。

[`dsh-session-checkpoint-policy/README.md`](../../node_modules/@deepseek-ai/dsh-session-checkpoint-policy/README.md) 的 Interrupted calls 与 Known Limitations 明确要求：没有结果的持久化调用恢复为 `TOOL_OUTCOME_UNKNOWN`，而非自动重试。产品必须保留这种不确定状态。对于可能产生副作用的操作，先核对实际状态或等待用户确认，不能让恢复流程自行重复执行。

取消也不等于撤销：`ABORTED_BEFORE_DISPATCH` 能说明工具体未执行；已经进入工具体或结果缺失的操作不能作同样承诺。Shell、网络、安装等副作用不因文件回滚而自动消失。

## 测试准备与证据规则

- 使用专用测试 Workspace，不在本产品代码库或用户真实项目中执行变更、故障注入和恢复实验。
- 首轮使用 clean Git 仓库与可核对内容的文本文件，建立小而可重复的验收样本。它只降低首轮验证复杂度，不预先裁定最终回滚支持边界。
- 为后续测试准备已有未提交修改、取消、权限拒绝、文件不可访问、并发修改、操作中断等场景。不能以 clean fixture 成功替代这些风险场景。
- 文件前后内容、Git 状态和工具结果是证据；模型自然语言总结只作辅助说明。
- 每次验收记录前置条件、操作、实际结果、Task / Session 关联、失败分类与复现方式。不得记录真实 API Key、Token、凭证或带认证参数的 URL。
- 需要模型调用的后续验收，必须使用用户另行允许的模型配置；本次审计没有进行该类验收。

## 必测的跨步骤场景

| 场景 | 必须观察到的行为 |
|---|---|
| Discuss 中请求变更 | 不依赖模型自律；既有约束阻止变更，fixture 前后状态一致 |
| 批准 Plan 后遇到需批准的工具 | 再次出现对应工具审批；Plan 批准不替代此审批 |
| 工具等待批准时拒绝 | 未派发的操作无副作用；任务状态准确记录拒绝，不显示成功 |
| 请求取消恰逢工具准备派发 | 能区分未派发取消与可能已产生影响，不统一显示已撤销 |
| 工作区原有未提交修改 | 原有修改不归到当前 Task；回滚不能覆盖它们 |
| 查看 diff 后用户修改同一文件 | 旧 diff 或回滚前提失效；重新核对，不覆盖新内容 |
| Tool call 持久化后、result 持久化前退出 | 恢复出现 unknown；不自动重复可能有副作用的调用 |
| Plan mode 切换 pending 时退出 | 恢复展示实际持久化状态，不凭上一次按钮状态声称已生效 |
| 回滚中途失败 | 明确部分完成范围、保留恢复材料；任务不能显示完整回滚成功 |
| Workspace 被移动或失去权限后恢复 | 明确提示绑定失效，不静默使用别的 cwd 或向错误目录写入 |

这些场景不要求重写 Harness 内部机制。产品层的工作是正确使用现有合同、显示真实状态，并在现有能力不足时阻止虚假成功和越界操作。

## Release Gates

### G0：现有基线与发布说明边界

当前自动化基线不是全绿：`npm test` 有 1 个失败，涉及 previous tag 选择受到 tag 别名影响。应先单独授权最小修复与隔离测试，使发布说明的 tag 边界稳定；不得把修复范围扩大到客户端更新系统。该修复不属于本次文档任务。

完成条件：相关测试与完整自动化检查均有实际运行结果，且未改变依赖、构建工具、Runtime 或更新安装行为。不能只记录“已知失败”然后将基线标为全通过。

### G1：Discuss 与执行授权

必须完成只读负面测试、Plan 批准与工具批准分离、拒绝不派发的证据。若现有公开配置无法提供 Discuss 所需限制，停止该能力发布并请求架构决策，不新增第二套权限实现。

### G2：完整 Change / Accept / Rollback

必须验证真实变更检测、任务前态保存、变更归属、接受语义、冲突检测、精确恢复和部分失败报告。没有这些能力，用户要求的闭环尚未完成。

下列支持边界待决，不在本文件中擅自排除：二进制、大文件、重命名、删除、新建未跟踪文件、符号链接、非 Git Workspace、任务前已有修改、并发用户修改、跨文件部分失败，以及命令造成的非文件副作用。每类都需要确定可保证的行为、明确限制与用户可理解的错误状态。

如果现有 Harness 缺少必要 seam，优先评估独立 Product Adapter / 桌面组件及公开插件接口，并单独确认实施方案。没有稳定扩展点时才评估最小 patch；不得为实现回滚新增 Agent Runtime 或擅自改变安全边界。

### G3：恢复与不确定结果

分别验证空闲、mode pending、审批等待、工具已完成、工具调用已持久化但结果缺失等恢复断点。最后一种必须显示 unknown 并要求核对，不承诺 exactly-once。持久化状态、当前运行状态与 UI 临时状态不能混用。

### G4：上游合同与平台验证

Product Adapter 只依赖已验证的当前 types / remotes / events；字段或能力缺失时明确标为 unknown / unsupported，不猜接口。自动化合约检查后，还需在 macOS Apple Silicon 实机完成以上完整闭环与负面场景。静态测试、GUI 入口存在和模型口头确认都不能替代真实文件、命令、审批、回滚及恢复验收。

## 推荐施工顺序

1. 单独授权处理 G0 的发布说明 tag 边界与隔离测试，保持客户端更新系统不变。
2. 产品首项代码改动：新增纯类型、无副作用的 Product Adapter projection 合同与测试，明确 Product Task 对 Harness Workspace / Session 的关联，准确保留 mode active / pending、tool outcome unknown 与 unsupported。
3. 用已核实的上游生命周期决定 Run 映射，不提前假定一个 Task 等于一个 turn，也不把临时运行标识当成可永久恢复 ID。
4. 验证 G1 及 G3 的现有机制；同时解决 G2 的 API 与变更前态缺口，形成明确实施决策。
5. 能力边界成立后，再按 [UI_SURFACE_MAP.md](UI_SURFACE_MAP.md) 的所有权与优先级实现最小呈现，并执行完整闭环验收。

第一项产品改动不包含首页、Work Panel、视觉改版、通用文件/Shell IPC、Runtime 调度、权限重写或凭证复制。本次仅新增文档，不执行上述施工步骤。
